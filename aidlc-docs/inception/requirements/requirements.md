## 2. 확정된 기술 스택 및 아키텍처 결정

명확화 질문(requirement-verification-questions.md)을 통해 확정된 기술 결정입니다.

| 영역 | 결정 | 비고 |
|------|------|------|
| **백엔드** | Node.js | Vercel Serverless Functions로 배포 |
| **프론트엔드** | React (Vite + SPA) | 단일 프로젝트, 라우팅으로 고객용(`/customer`)·관리자용(`/admin`) 분리 |
| **데이터베이스** | Supabase (PostgreSQL 기반) | 무료 티어 |
| **인증** | Supabase Auth | 관리자 인증(JWT, bcrypt 대체), 16시간 세션 |
| **실시간** | Supabase Realtime | 직접 SSE 구현 대신 사용 (Vercel 서버리스가 장시간 연결에 부적합) |
| **스토리지** | Supabase Storage | 메뉴 이미지 업로드 (무료 티어 1GB) |
| **배포** | Vercel (Hobby, 무료) | 프론트 SPA + Node.js Serverless Functions |
| **멀티테넌시** | 단일 매장 | MVP 단계에서 하나의 매장만 운영 |
| **관리자 계정** | 시드(seed) 데이터로 생성 | Supabase Auth 사용자로 초기 시딩 |
| **예상 규모** | 소규모 | 단일 매장, 동시 20명 이내 |

### 2.1 아키텍처 개요

```
+-------------------------+
|   React SPA (Vite)      |
|   /customer  /admin     |
+-------------------------+
        |          |
        |          +-----------------------------+
        v                                        v
+-------------------------+        +----------------------------+
| Vercel Serverless (API) |        | Supabase                   |
| Node.js REST endpoints  |------->| - PostgreSQL (data)        |
| (주문/메뉴 CRUD 등)     |        | - Auth (관리자 인증)       |
+-------------------------+        | - Realtime (실시간 주문)   |
                                   | - Storage (메뉴 이미지)    |
        관리자 대시보드 실시간 구독 ---> +----------------------------+
        (프론트가 Supabase Realtime에 직접 연결)
```

**핵심 설계 원칙**:
- 실시간 주문 모니터링은 관리자 프론트엔드가 Supabase Realtime에 직접 구독하여 처리 (Vercel 서버리스는 짧은 API 요청만 담당)
- 요구사항 원문의 "SSE" 표기는 "실시간 업데이트" 의도로 해석하여 Supabase Realtime으로 구현

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 고객용 기능 (Customer Features)

**FR-C-01: 테이블 태블릿 자동 로그인 및 세션 관리**
- 관리자가 1회 초기 설정: 매장 식별자, 테이블 번호, 테이블 비밀번호 입력
- 로그인 정보 로컬 저장 후, 이후 자동 로그인

**FR-C-02: 메뉴 조회 및 탐색**
- 메뉴 화면이 기본 화면으로 항상 표시
- 카테고리별 분류, 메뉴 상세(메뉴명/가격/설명/이미지)
- 카드 형태 레이아웃, 터치 친화적 버튼(최소 44x44px)

**FR-C-03: 장바구니 관리**
- 메뉴 추가/삭제, 수량 조절, 총 금액 실시간 계산, 장바구니 비우기
- 클라이언트 측 임시 저장 (페이지 새로고침 시에도 유지)
- 서버 전송은 주문 확정 시에만 수행

**FR-C-04: 주문 생성**
- 주문 내역 최종 확인 및 확정
- 성공 플로우: 주문 번호 표시 → 장바구니 자동 비우기 → 메뉴 화면 자동 리다이렉트(5초)
- 실패 시: 에러 메시지 표시, 장바구니 유지
- 주문 정보: 매장/테이블 식별 정보, 메뉴 목록(메뉴명/수량/단가), 총액, 세션 ID

**FR-C-05: 주문 내역 조회**
- 주문 시간 순 정렬, 주문별 상세(번호/시각/메뉴/금액/상태)
- 현재 테이블 세션 주문만 표시 (이전 세션 및 이용 완료 주문 제외)
- 페이지네이션 또는 무한 스크롤

### 3.2 관리자용 기능 (Admin Features)

**FR-A-01: 매장 인증**
- 매장 식별자 + 사용자명/비밀번호 입력
- Supabase Auth 기반 JWT 인증, 16시간 세션 유지, 새로고침 시 세션 유지, 16시간 후 자동 로그아웃

**FR-A-02: 실시간 주문 모니터링**
- Supabase Realtime 기반 주문 목록 실시간 업데이트 (2초 이내 표시 목표)
- 그리드/대시보드 레이아웃: 테이블별 카드, 총 주문액, 최신 주문 미리보기
- 주문 카드 클릭 시 전체 메뉴 상세 보기
- 주문 상태 변경(대기중/준비중/완료), 신규 주문 시각적 강조
- 테이블별 필터링

**FR-A-03: 테이블 관리**
- 태블릿 초기 설정(테이블 번호/비밀번호, 16시간 세션 생성, 자동 로그인 활성화)
- 주문 삭제(직권 수정): 확인 팝업 → 즉시 삭제 → 총 주문액 재계산
- 테이블 세션 처리: 세션 시작(첫 주문)/종료(이용 완료) 관리
  - 종료 시 해당 세션 주문을 과거 이력으로 이동, 현재 주문 목록/총액 0으로 리셋
- 과거 주문 내역 조회: 테이블별 시간 역순, 날짜 필터링

**FR-A-04: 메뉴 관리**
- 카테고리별 조회, 등록(메뉴명/가격/설명/카테고리/이미지), 수정, 삭제, 노출 순서 조정
- 이미지: Supabase Storage 업로드
- 데이터 검증: 필수 필드, 가격 범위

## 5. 보안 요구사항 (Security Baseline — 경량 적용)

워크샵/MVP 성격에 맞춰 **방향성 가이드**로 적용합니다. 개발 속도를 막는 blocking 제약은 아니지만, 인증/비밀번호/세션을 다루므로 아래 항목을 우선 반영합니다.

| 규칙 | 적용 방향 |
|------|-----------|
| SECURITY-05 입력 검증 | 모든 API 파라미터 타입/길이/형식 검증, 파라미터화 쿼리 (Supabase 클라이언트 사용) |
| SECURITY-08 접근 제어 | 관리자 라우트 서버 측 권한 검사, 리소스 소유권 확인, JWT 서버 측 검증 |
| SECURITY-12 인증/자격증명 | 비밀번호 해싱(Supabase Auth 내장), 세션 만료/무효화, 하드코딩 자격증명 금지, 시크릿 매니저 사용 |
| SECURITY-15 예외 처리 | 외부 호출 에러 핸들링, fail-closed, 사용자에게 일반화된 에러 메시지 |
| 기타 규칙 | 프로덕션 전환 시 재검토 (인프라 관련 규칙은 현 단계 N/A 가능) |

> Supabase Auth가 비밀번호 해싱, JWT 발급/검증, 세션 관리 등 핵심 보안 기능을 제공하므로 상당 부분 위임됩니다.

## 6. 테스트 전략 (Property-Based Testing — Partial 적용)

Partial 모드로 순수 함수 및 직렬화 계산 로직에 PBT를 적용합니다 (PBT-02, 03, 07, 08, 09 enforced).

| 대상 로직 | PBT 속성 |
|-----------|----------|
| 장바구니 총 금액 계산 | Invariant (수량×단가 합계 = 총액), 빈 장바구니 경계값 |
| 주문 총액 재계산 (주문 삭제 후) | Invariant (남은 주문 합계 = 재계산 총액) |
| 주문 데이터 직렬화/역직렬화 | Round-trip (serialize → deserialize = identity) |
| 세션 주문 그룹화/필터링 | Invariant (현재 세션 주문만 반환, 개수 보존) |

- 프레임워크: **fast-check** (JS/TS, Vitest 통합)
- CRUD/UI 위주 로직은 PBT 대상에서 제외 (예제 기반 테스트로 커버)

## 7. MVP 범위 (구현 대상)

**고객용**: 자동 로그인/세션, 메뉴 조회, 장바구니, 주문 생성(5초 후 리다이렉트), 주문 내역 조회(현재 세션)

**관리자용**: 매장 인증(16시간), 실시간 주문 모니터링(그리드, Realtime), 테이블 관리(초기 설정/주문 삭제/이용 완료/과거 내역)

---

## 8. 제외 범위 (Out of Scope)

`constraints.md` 기준 아래 기능은 구현하지 않습니다:
- **결제**: 실제 결제, PG 연동, 영수증, 환불, 포인트/쿠폰
- **인증/보안**: OAuth/SNS 로그인, 2FA/OTP
- **파일/컨텐츠**: 이미지 리사이징/최적화, CMS, 광고
- **알림**: 푸시/SMS/이메일/소리·진동
- **주방**: 주문 주방 전달, 재고 관리
- **고급 기능**: 데이터 분석, 매출 리포트, 재고, 직원 관리, 예약, 리뷰, 다국어
- **외부 연동**: 배달 플랫폼, POS, SNS 공유, 지도/번역 API

## 9. 용어 정의

- **MVP**: Minimum Viable Product (최소 기능 제품)
- **테이블 세션**: 특정 테이블에 고객이 앉아 첫 주문을 시작한 후부터 해당 테이블 이용 완료 처리까지의 기간. 세션 종료 후 다른 고객의 첫 주문 시 새 세션 시작.
- **BaaS**: Backend-as-a-Service (Supabase)
- **SPA**: Single Page Application

---

## 10. 주요 요구사항 요약

- 단일 매장 대상 테이블오더 MVP, 무료 스택(Vercel + Supabase)으로 구축
- 고객용/관리자용을 하나의 React SPA에서 라우팅 분리
- 실시간 주문 모니터링은 Supabase Realtime으로 구현 (직접 SSE 대체)
- 관리자 인증/이미지 저장은 Supabase Auth/Storage 활용
- 보안은 경량 방향성 가이드, PBT는 계산 로직 중심 Partial 적용
